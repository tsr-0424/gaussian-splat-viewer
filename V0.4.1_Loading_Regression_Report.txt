V0.4.1 Loading Regression Report
日期：2026-10-02

1. Root Cause
V0.4 增加了「小 main → projects.json → dynamic import 整包 Viewer（含 Spark/Three）→ UI/Renderer → model fetch」串行 critical path。V0.3 則由 HTML 直接開始載入含 Viewer 的 initial bundle；V0.4 多出的 manifest/import 邊界把 library 請求延後，且模型 fetch 被完整 library 的 download/parse/evaluation 擋住。
原 V0.4 debug 又在 renderer/model 前 await 多個診斷模組。這影響 debug，不能把它誤稱正常 production 也下載 profiler。
Viewer UI 與 Spark/Three 混在約 3MB chunk；UI 改動會改整包檔名，不能沿用舊版大包快取。已確認 library 版本及模型不變，bundle 增量很小，主因是啟動順序與資源／快取邊界，並非 PLY 增大。
此前將 Viewer JS 約5.5秒只當作量測結果，未以 V0.3 同條件對照阻擋發布，這是判斷不足。本次直接比較 Git 原始碼並實測修復，不從總時間猜原因。
歷史5.5秒沒有完整 network/CPU trace，因此不能把每一秒確定歸因於下載或 evaluation，也不推測 iPhone 為何較快。

2. V0.3 vs V0.4 diff
A：309df5e，V0.3 最後正常版本。B：b23e239，修正前 V0.4。C：本次 V0.4.1。
main：static Viewer import 改成 catalog 完成後 dynamic import。
ProjectPages：原 B 在 main 靜態匯入；C 僅非 Viewer 路由匯入。
ViewerSession：B 在開始 load 前初始化 UI 並等待 debug；C fetch 已開始，debug 延後到 first-frame/ready 後。
LoadingProfiler：只在 debug 使用，原 production 本來就沒有這個 bundle，不是 production seconds-gap 的直接來源。
FirstSplatVisibility：B production 也做 readPixels 並 gate Ready；C production 不建立 probe，保持 V0.3 render-ready criterion。debug 保留精確取樣。
Vite：原 B 的 Spark/Three 都在同一 Viewer chunk，並不是三個依序下載的 vendor requests；C 分離並條件式 modulepreload。
Manifest：只有一次小 JSON 請求，沒有重試、runtime SHA256 或大型同步計算；C build-time 嵌入同一份 catalog，省掉這次 round trip。不改 Project schema。
Model URL：同樣 SHA256 路徑的原始 PLY，沒有 redirect/新的來源／新的模型格式。
Production verification：僅建置時執行，沒有 browser dependency；不是載入等待來源。

5. Critical path
舊 B：HTML→小main→manifest→整包Viewer/Spark→UI/renderer→model request→decode/scene→render。
新 C：HTML→小main/catalog→立即model fetch；同時 HTML modulepreload Viewer/Three/Spark→renderer/camera→consume同一response stream→scene→render。
Gallery：只在 Gallery/Project 路由下載。Debug/Benchmark/PerformancePanel：ready 後才 import，不 gate 首幀。控制與品質功能保留。
初次未快取的 library 約1.03MB HTTP gzip仍需下載；若仍慢，剩餘成本可能就在此 library request/evaluation 或模型 response/scene/render phase，要讀 waterfall，不以其他裝置體感推測。

7. 為什麼會變慢
同樣 vendor bytes 的下載開始較晚，model fetch 還被延遲到 vendor 完成。大型 chunk 隨 UI 改動失去旧缓存時，這段 serial wait 尤其明顯。debug 額外 await 與 visibility gate 又增加首幀前工作。
本機完全冷 HTTP 快取下 B 相較 A 首幀中位數只慢83ms；不能宣稱重現了歷史5.5秒或所有手機的嚴重程度。已證明啟動架構缺陷與修復效果，仍需實體裝置／真實公網 trace 驗證。

8. 如何修復
Embedded build-generated catalog，不等 JSON network；直接 Viewer 不匯入 Gallery。
在 route 找到 URL 的同一 tick beginModelRequest，再 await Viewer。原始 response/body 傳給 Spark，沒有 clone、第二份 JS PLY buffer、格式轉換或資料刪減；換路由 abort 早期請求。
只對直接 Viewer/legacy model URL 注入 modulepreload，沒有盲目 preload 所有工具。分離穩定 Spark/Three chunks。
Debug 在 ready 後初始化，暫存 startup 事件後 replay，仍可量測最初 model request。response headers timestamp 在 fetch promise resolve 時記錄，避免把等待 library 當 headers latency。
Production 不執行 FirstSplatVisibility，仍用 V0.3 已排序 splats 已提交的 readiness。

13. FPS
Cold三版本中位數約74.99FPS。快速連續warm啟動的C首2秒中位數67.88FPS，原始值不隱藏。
後續同時段隔離其他本次建立的Viewer分頁，再比較三個2秒rolling窗口：A中位67.81、B67.96、C68.16FPS；C樣本為68.16／54.79／74.99，波動已保留。此前單獨跑C三品質固定視角8秒測量為HIGH67.89、MEDIUM67.94、LOW68.04。
未觀察到穩定的C特有效能下降，但不能由這些短樣本承諾每台／每時段固定75FPS，也不臆測波動原因。沒有改pixel ratio presets、Gaussians、SH、LOD或camera renderer設定。
